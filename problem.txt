在多用户公网部署场景中（例如：服务方部署了网关和多个 Agent，供外部用户注册使用），用户应如何获取虚拟 API Key（VSK）？
由于网关程序运行在服务方服务器上，用户无法直接执行类似 main.go --gen_vsk 的本地命令来生成 VSK。
是否合理的流程是：用户通过网关前端（如 Web 控制台）提交自己的真实 API Key，然后由前端返回一个虚拟 API Key，用户再将其配置到 Agent 的配置文件或界面中？
另外，如果网关治理系统（如我们借鉴的SAGA）是纯命令行的，这种交互方式又如何实现？

```
A公司部署了 AegisGuard + OpenClaw 等多个 Agent
外网用户注册 OpenClaw 账号（与 AegisGuard 无关）
用户自己有 OpenAI Key
用户想让 OpenClaw 经过 AegisGuard 的安全网关
```

## 用户获取 VSK 的流程

**用户需要访问一个管理界面来提交真实 Key 并换取 VSK。** 这个界面必须是 AegisGuard 的一部分，因为 VSK 是 AegisGuard 签发的。

具体实现：

### 方案：网关增加一个公开的自助端点

```
POST /vkeys/self-serve
Body: {
  "real_api_key": "sk-user-own-key",
  "agent_name": "openclaw"
}
Response: {
  "vsk": "vsk-a1b2c3d4-e5f6"
}
```

**流程：**
1. 用户在 OpenClaw 界面看到提示："接入 AegisGuard 安全网关，请前往 `https://aegis.a-company.com/vkeys/setup`"
2. 用户打开这个页面，粘贴自己的真实 OpenAI Key
3. 网关生成 VSK，返回给用户
4. 用户复制 VSK 到 OpenClaw 的配置里

### 但这里有个安全问题

`/vkeys/self-serve` 如果完全开放，任何人都能调。需要加一层防护：

**加一个 Setup Token（一次性凭证）：**

1. A公司管理员在后台生成一个 Setup Token：`setup-abc123`
2. A公司把这个 Token 放在 OpenClaw 的用户引导页面里
3. 用户调用时带上这个 Token：
   ```
   POST /vkeys/self-serve
   Body: {
     "setup_token": "setup-abc123",
     "real_api_key": "sk-user-own-key"
   }
   ```
4. 网关验证 Setup Token 有效后，生成 VSK 并立即销毁该 Token

这样只有拿到 Setup Token 的用户才能注册 VSK，不是完全开放的。

# 二、你当前方案的核心问题（重点）

## ❌ 问题1：你在“收集用户真实 API Key”

这是最大的问题。

用户 → 提交 sk-xxx → 你存储

这意味着：

而行业最佳实践是：

👉 **尽量避免收集用户的原始 API Key**

你加的：

```
setup_token
```

本质只是：

* 防止“所有人乱调接口”
* 但不能证明“这个用户是谁”

👉 它不是身份认证（authentication）



## ❌ 问题3：VSK = 长期凭证 → 暴露风险

你现在设计：

```
VSK = 长期不变
```

问题是：

* 一旦 VSK 泄露
* 攻击者就可以一直调用（除非你吊销）

而现实里：

👉 API key 应该“限制范围 + 可撤销 + 可追踪” ([Google Cloud][2])

POST /vkeys/self-serve

setup_token = {

# 一、你这个方案对不对？——对，但“危险地接近反模式”

你做的核心事情其实是：

> 用 `/vkeys/self-serve` 把 **用户真实 API Key → VSK 映射**

这在架构上是合理的，甚至是行业常见思路（代理 + 凭据托管）。

但问题在于——你现在的入口设计：

```
用户提交真实 API Key → 服务器返回长期 VSK
```

**这一步在安全领域是一个高风险点。**

原因很简单：

👉 API Key 本质是“长期凭证”，一旦暴露就是完全接管
👉 现实中大量泄露都来自“正常流程传播”而不是攻击 ([levo.ai][1])
